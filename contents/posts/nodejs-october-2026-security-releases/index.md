Node.js가 10월 21일 지원 중인 세 라인 모두에 보안 릴리스를 냈다. 올릴 버전은 `22.23.4`, `24.22.1`, `26.12.1`이다. 고쳐진 CVE는 10건이고 그중 High가 4건인데, TLS 인증서 호스트 검증 우회 두 건과 Brotli 디코더의 원격 코드 실행이 들어 있다. 외부 HTTPS 호출을 하거나 압축된 요청, 응답을 다루는 백엔드라면 거의 다 해당된다는 얘기다. 미루지 않고 올리는 쪽이 맞아 보인다.

> 이번 릴리스에서 무엇이 고쳐졌고, 어떤 서비스가 먼저 올려야 하나?

> 이 글은 Node.js 보안 릴리스 공지와 v24.22.1 릴리스 노트를 확인해 정리했다. 공지에는 CVE별 상세 설명이 거의 없어서, 제목과 커밋 메시지에서 읽히는 범위까지만 적었다.

## 1. High 등급 4건

| CVE               | 영역   | 내용                                              | 영향 라인              |
| ----------------- | ------ | ------------------------------------------------- | ---------------------- |
| `CVE-2026-105482` | DNS    | `dns.resolve`가 NUL 문자가 든 이름을 잘라서 처리  | `26.x`, `24.x`, `22.x` |
| `CVE-2026-105483` | TLS    | 전각 숫자로 쓴 IP에서 인증서 호스트 검증 우회     | `26.x`, `24.x`         |
| `CVE-2026-106069` | TLS    | 호스트가 느슨하게 IP로 해석될 때 호스트 검증 우회 | `26.x`, `24.x`, `22.x` |
| `CVE-2026-111497` | Brotli | 디코더 out-of-bounds write로 원격 코드 실행 가능  | `26.x`, `24.x`, `22.x` |

공지를 보니 TLS 쪽이 가장 눈에 걸렸다. 두 건 모두 "호스트 이름이 IP처럼 보일 때" 검증이 어긋나는 문제다. 릴리스 노트의 커밋 제목은 `tls: reject non-canonical IP addresses`와 `tls: fix ip normalization regression`이다. 표준 형태가 아닌 IP 표기를 이제 거부한다는 뜻으로 읽힌다. Medium 등급인 `CVE-2026-106072`(비표준 IPv4 호스트 이름에서 DNS SAN이 IP 엔드포인트를 인증해 버리는 문제)도 같은 커밋에서 고쳐졌다.

사용자 입력으로 받은 URL에 서버가 대신 요청을 보내는 구조라면 특히 신경 쓸 부분이다. 웹훅 전송, 이미지 프록시, 링크 미리보기 같은 기능이 그렇다.

Brotli 건은 공지에 설명이 딱 한 줄이다. 디코더의 out-of-bounds write가 원격 코드 실행으로 이어질 수 있다는 것. 수정은 상위 brotli 저장소의 커밋을 cherry-pick하는 방식으로 들어갔다. **`zlib`의 Brotli 압축 해제를 외부 입력에 쓰는 서버**라면 이번 릴리스에서 가장 급한 항목이다.

## 2. Medium, Low 등급

나머지 6건은 이렇다.

- `CVE-2026-105481`(Medium): keep-alive 소켓이 요청을 보내기 전에 도착한 응답을 처리하는 문제
- `CVE-2026-106072`(Medium): 위에서 말한 비표준 IPv4 호스트 이름 검증 문제
- `CVE-2026-106074`(Medium): `crypto.randomUUID()`와 `randomInt()`의 엔트로피 캐시가 사용자 시작 스냅샷과 SEA(single executable application)에 저장돼, 모든 프로세스가 같은 값을 반복
- `CVE-2026-106070`(Low, 26.x): ZIP 헤더 검증 실패 뒤에도 공격자가 조작한 앞부분 바이트를 돌려주는 문제
- `CVE-2026-106071`(Low, 26.x): Permission Model 와일드카드 조회에서 파일 시스템 권한이 과하게 허용되는 문제
- `CVE-2026-106073`(Low): `fs.realpathSync`로 Permission Model을 우회하는 문제

개인적으로는 `randomUUID()` 건이 의외였다. 스냅샷이나 SEA로 배포하는 경우에만 해당하지만, 해당한다면 프로세스마다 같은 UUID가 나온다는 뜻이다. 그 UUID를 요청 ID 정도가 아니라 토큰이나 키로 쓰고 있었다면 영향이 크다.

## 3. 같이 올라간 의존성

| 의존성      | 24.22.1 기준 버전 | 해당 라인              |
| ----------- | ----------------- | ---------------------- |
| undici      | `7.30.1`          | `26.x`, `24.x`, `22.x` |
| OpenSSL     | `3.5.9`           | `24.x`, `22.x`         |
| c-ares      | `1.34.9`          | `26.x`, `24.x`, `22.x` |
| 루트 인증서 | NSS `3.131.1`     | `26.x`, `24.x`, `22.x` |

루트 인증서 갱신은 eMudhra 중간 CA 침해 건 때문이다. SQLite 업데이트는 22.x에만 들어갔다. 버전 번호는 v24.22.1 릴리스 노트에서 확인한 값이고, 다른 라인은 각 릴리스 노트를 따로 봐야 한다.

## 4. 올리기 전에 확인할 것

지금 돌고 있는 런타임과 번들된 라이브러리 버전은 이렇게 본다.

```bash
node -v
node -p "process.versions"
```

`process.versions`에 `openssl`, `undici`, `ares` 같은 항목이 같이 나온다. 컨테이너를 쓴다면 베이스 이미지 태그가 실제로 새 버전을 가리키는지도 확인해 둔다.

- 운영 중인 라인이 `22.23.4`, `24.22.1`, `26.12.1` 이상인지
- 지원이 끝난 라인(EOL)을 쓰고 있지 않은지. 공지는 EOL 버전이 보안 릴리스마다 항상 영향을 받는다고 적고 있다.
- 사용자 입력 URL로 HTTPS 요청을 보내는 기능이 있는지
- 외부 입력을 Brotli로 압축 해제하는 경로가 있는지
- 스냅샷이나 SEA로 배포하면서 `randomUUID()`를 보안 용도로 쓰는지
- TLS 쪽 변경으로 비표준 IP 표기를 쓰던 호출이 실패하지 않는지
