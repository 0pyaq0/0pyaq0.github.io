10월 28일 Node.js 26.13.0이 나오면서 **26.x가 LTS(Long Term Support)로 전환됐다**. 코드명은 'Lithium'이고 지원은 2029년 4월 말까지다. 다음 날에는 27의 첫 알파가 나왔다. 이번 27부터 메이저 릴리스가 1년에 한 번으로 줄고 홀수·짝수 구분이 사라진다. 운영 중인 서비스 입장에서는 "언제 어떤 버전으로 올릴지"를 정하는 기준이 바뀐 셈이다.

> Node 26 LTS로 지금 올려도 되는지, 그리고 바뀐 릴리스 일정에서 27 알파는 누가 언제 봐야 하는가?

> 이 글은 Node.js 공식 블로그의 26.13.0, 27 알파 릴리스 노트와 릴리스 일정 공지, 이전 릴리스 페이지를 읽고 정리했다. 새 일정은 공지에 확정이 아니며 바뀔 수 있다고 적혀 있다.

## 1. 26.13.0에서 실제로 바뀐 것

릴리스 노트를 보면 26.13.0은 코드 변경이 거의 없다. `process.release` 같은 메타데이터를 LTS로 바꾼 것 외에는 26.12.1과 같다고 명시돼 있다. 그러니 26.12.x를 이미 쓰고 있다면 동작상 차이는 없다.

신경 쓸 부분은 22나 24 같은 이전 LTS에서 바로 넘어오는 경우다. 노트에 Node.js 25부터 Linux 공식 바이너리가 `libatomic`에 링크돼 있어서 배포판에 따라 따로 설치해야 할 수 있다는 경고가 붙어 있다. LTS끼리만 올리는 팀이라면 이번에 처음 만나는 변화다.

```bash
# 실행 중인 바이너리가 LTS인지, 어떤 이름인지 확인
node -p "process.release.lts"   # Lithium

# 공식 Linux 바이너리가 libatomic을 찾는지 확인
ldd "$(command -v node)" | grep atomic
```

이전 릴리스 페이지 기준으로 지금 지원 중인 라인은 이렇다.

| 버전  | 코드명  | 상태 | 비고              |
| ----- | ------- | ---- | ----------------- |
| `v27` | 없음    | 알파 | 운영 사용 금지    |
| `v26` | Lithium | LTS  | 2029년 4월 말까지 |
| `v24` | Krypton | LTS  | 계속 패치 중      |
| `v22` | Jod     | LTS  | 계속 패치 중      |

`v25`와 `v20`은 이미 EOL이다. 같은 페이지에 운영 애플리케이션은 Active LTS나 Maintenance LTS만 쓰라는 문구가 그대로 있다.

## 2. 27부터 바뀌는 릴리스 일정

공지에 따르면 26이 기존 방식의 마지막, 27이 새 방식의 첫 라인이다.

- 메이저는 1년에 한 번, 4월에 나온다.
- 10월부터 3월까지 6개월은 알파, 4월부터 10월까지 6개월은 Current, 그 뒤 30개월은 LTS다.
- 홀수·짝수 구분이 없어지고 모든 메이저가 LTS가 된다.
- 첫 Current 릴리스부터 EOL까지 총 36개월이다.

공지에 실린 예정표 일부를 옮기면 다음과 같다.

| 버전   | 알파 시작   | Current    | LTS 전환    |
| ------ | ----------- | ---------- | ----------- |
| `27.x` | 2026년 10월 | 2027년 4월 | 2027년 10월 |
| `28.x` | 2027년 10월 | 2028년 4월 | 2028년 10월 |
| `29.x` | 2028년 10월 | 2029년 4월 | 2029년 10월 |

27의 EOL은 2030년 4월로 잡혀 있다. 매년 10월에 새 LTS가 생기니 업그레이드 일정을 1년 주기로 고정하기 쉬워졌다.

## 3. 알파 채널은 누구를 위한 것인가

알파는 예전 홀수 릴리스가 하던 조기 테스트 역할을 맡는다. 다만 결정적인 차이가 있다. **알파 기간에는 semver-major 변경이 계속 들어올 수 있다.** 버전도 `27.0.0-alpha.1` 같은 semver 프리릴리스 형식을 따른다.

공지가 밝힌 대상은 라이브러리 작성자와, 다가올 호환성 깨짐을 미리 확인하려는 CI 파이프라인이다. 운영 사용은 대상이 아니라고 못 박았다. Nightly와 달리 서명·태그되고 CITGM 테스트를 거친다.

서비스 팀이라면 CI에 알파를 비차단 잡으로 하나 넣어 두는 정도가 현실적인 활용법으로 보인다.

## 4. 27 알파에서 미리 봐 둘 변경

첫 알파 노트에 semver-major 변경이 많다. 최종 27.0.0에서 달라질 수 있지만 백엔드에 닿는 것만 골랐다.

### 메모리와 직렬화

V8이 14.6에서 15.6으로 올라간다. 개인적으로는 힙 기본값 변경이 가장 걸렸다. `--max-old-space-size`를 지정하지 않으면 기본 힙 한도가 물리 메모리의 절반이 되고, 256MB에서 4GB 사이로 제한된다. 또 `Buffer`와 `ArrayBuffer`가 차지한 메모리도 힙 한도에 포함된다. 노트는 기존 기본값에 기대던 앱이라면 이 옵션을 명시하라고 권한다.

`v8.serialize()`, `structuredClone()`, `postMessage()`가 쓰는 직렬화 포맷도 바뀌어서 이전 버전 Node.js가 읽지 못한다. 직렬화한 결과를 캐시나 큐에 넣고 다른 버전 프로세스가 꺼내 쓰는 구조라면 혼합 배포 구간에서 문제가 된다.

### HTTP와 보안 관련

- `keepAliveTimeout` 기본값이 65초가 된다. 앞단 로드밸런서의 유휴 타임아웃과 맞춰 둔 값이 있다면 다시 비교해 본다.
- `req.headers`가 null 프로토타입 객체가 된다. `req.headers.hasOwnProperty(...)` 같은 호출은 깨진다.
- 헤더 한도를 넘는 응답은 거부된다.
- OpenSSL 3 이상이 필요하고, 번들 FIPS 프로바이더 빌드와 OpenSSL 엔진 지원이 빠진다.
- `domain` 모듈은 런타임 경고 대상이 되고, `--allow-env` 권한이 추가된다.

npm은 12.1.0으로 올라간다.

### 점검 목록

- 22·24에서 26으로 올릴 때 베이스 이미지에 `libatomic`이 있는지 확인한다
- 운영 런타임 버전을 26 LTS 기준으로 다시 잡는다
- CI에 27 알파를 비차단 잡으로 추가할지 정한다
- `--max-old-space-size`를 기본값에 맡기던 서비스를 목록으로 만든다
- `req.headers.hasOwnProperty`와 `domain` 사용처를 검색해 둔다
