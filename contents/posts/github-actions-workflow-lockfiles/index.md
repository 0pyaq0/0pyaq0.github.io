GitHub Actions에 워크플로 lockfile이 public preview로 들어왔다. `uses: actions/checkout@v4`처럼 태그로 적어 둔 액션을 `.github/workflows/actions.lock`에 기록한 커밋으로 고정해서 실행한다. 태그가 나중에 다른 커밋으로 옮겨져도 실행되는 코드는 리뷰한 시점 그대로다. 지금까지 공급망 공격을 막으려면 워크플로 파일마다 40자리 SHA를 박아 넣어야 했는데, 공식 문서는 lockfile을 쓰는 저장소라면 그럴 필요가 없다고 적고 있다.

> 액션 태그가 바뀌어도 리뷰한 코드만 돌게 하려면 무엇을 해야 하고, lockfile은 기존 SHA 핀과 무엇이 다른가?

> 이 글은 GitHub Changelog의 10월 14일 발표, Actions 공식 문서의 workflow dependency lockfiles 페이지, gh-actions-lock 저장소 README를 읽고 정리했다. public preview이고 CLI도 1.0 이전 버전이라 형식과 옵션은 바뀔 수 있다.

## 1. 왜 lockfile이 필요한가

태그와 브랜치는 움직인다. 리뷰할 때 `v3.1.0`이 가리키던 커밋과 다음 달 실행할 때 가리키는 커밋이 같다는 보장이 없다. 액션 저장소가 탈취되면 내 저장소에는 아무 변경이 없는데도 다음 실행부터 악성 코드가 돈다. changelog가 든 이유도 정확히 이 시나리오다.

기존 해법은 SHA 핀이었다.

```yaml
- uses: actions/checkout@<40자리 커밋 SHA> # v4
```

동작은 확실하지만 읽기 불편하고, 업데이트할 때마다 SHA와 주석을 같이 고쳐야 한다. 내가 쓴 액션이 내부에서 또 다른 액션을 태그로 부르면 그쪽은 여전히 움직인다는 문제도 남는다. lockfile은 워크플로 파일은 태그 그대로 두고, 고정은 별도 파일이 맡는 방식이다. npm의 `package-lock.json`과 비슷한 역할이다.

## 2. lockfile에 무엇이 기록되나

공식 문서에 실린 형식은 이렇다.

```yaml
# This file is machine-generated by `gh actions-lock`.
# Do not edit by hand; run `gh actions-lock` to update.
version: "v0.0.2"
workflows:
  ".github/workflows/ci.yml":
    - "octo-org/deploy-action@v3.1.0"
dependencies:
  "octo-org/deploy-action@v3.1.0":
    ref: "v3.1.0"
    commit: "sha1-..."
    owner_id: 44036562
    repo_id: 197814629
```

눈여겨본 건 `owner_id`와 `repo_id`다. 커밋만이 아니라 저장소의 숫자 ID까지 기록하고, 실행 시점에 이름 뒤에 있는 저장소가 잠글 때와 같은지 확인한다. 저장소 이름을 삭제한 뒤 같은 이름으로 다시 만드는 식의 하이재킹도 걸러진다는 뜻이다. 잠근 커밋은 원본 저장소의 어떤 브랜치 안에 있어야 한다.

적용 범위는 이렇다.

| 대상                  | lockfile 적용                 |
| --------------------- | ----------------------------- |
| 직접 쓰는 액션        | 기록한 커밋으로 실행          |
| 액션이 부르는 액션    | 전이 의존성까지 기록          |
| 재사용 워크플로       | 정의된 저장소의 lockfile 기준 |
| 같은 저장소 로컬 액션 | 현재 미지원, 온보딩에서 제외  |

재사용 워크플로는 조금 헷갈린다. changelog에는 재사용 워크플로 의존성도 고정한다고 적혀 있는데, 문서에는 재사용 워크플로 호출은 확장되지 않고 그 워크플로가 정의된 저장소의 lockfile이 다룬다고 나온다. 사내 공용 워크플로 저장소를 쓰고 있다면 그 저장소에도 lockfile을 만들어야 끝까지 고정된다고 읽는 게 안전하겠다.

## 3. 만들고 갱신하는 방법

lockfile은 GitHub CLI 확장으로 만든다. 직접 편집하지 않는다.

```bash
gh extension install github/gh-actions-lock

# .github/workflows/ 아래 모든 워크플로를 훑어 액션을 SHA로 고정하고 lockfile 갱신
gh actions-lock
```

새 워크플로를 만들었거나 기존 워크플로에서 `uses` 의존성을 추가·삭제했다면 다시 실행한다. 디렉터리 전체를 대상으로 돌리면 삭제된 워크플로의 항목과 고아가 된 의존성도 같이 정리한다. 특정 워크플로만 지정해서 돌리면 다른 항목은 건드리지 않는다.

태그가 정상적으로 새 커밋으로 옮겨 갔을 때는 옵션이 따로 있다.

- `--relock`: 정상적으로 움직인 ref를 다시 해석해서 새 SHA로 기록
- `--accept-moved`: 기록된 커밋이 원본에서 더 이상 닿지 않는 의심스러운 경우까지 다시 해석
- `--no-migrate-local-actions`: 같은 저장소의 `./...` 참조를 `$/...`로 바꾸지 않음

`--accept-moved`가 별도인 게 마음에 들었다. 기록한 커밋이 원본에서 사라졌다는 건 강제 푸시나 저장소 변조 가능성이 있다는 뜻이라, **기본값으로는 오류로 남겨 두고 사람이 판단하게 한다.** 무심코 넘기면 안 되는 상황을 도구가 구분해 주는 셈이다.

Dependabot도 연동된다. 온보딩한 워크플로의 액션 버전을 올리는 PR을 Dependabot이 열면 같은 PR에서 lockfile 항목도 다시 만든다. 따로 설정할 건 없다.

## 4. 강제 정책과 지금의 제약

워크플로를 한 번 온보딩하면 그 워크플로가 쓰는 모든 액션 의존성이 lockfile에 있어야 한다. 실행 시에는 기록된 커밋이 돌고, 허용 액션 정책도 그 커밋을 기준으로 검사한다. 엔터프라이즈, 조직, 저장소 관리자가 범위 전체에 lockfile을 요구하는 **Require lockfile** 정책도 같이 public preview로 나왔다.

도입 전에 알아 둘 제약도 꽤 있다.

- 대상은 GitHub Enterprise Cloud와 데이터 레지던시 버전이다. 다른 플랜과 GHES는 발표에 나오지 않는다.
- lockfile이 있는 워크플로에서는 로컬 경로 액션을 쓸 수 없고 온보딩에서 빠진다. README는 이를 단기적인 공백이라고 적고 있다.
- gh-actions-lock은 1.0 이전 Technical Preview라 lockfile 형식과 플래그가 바뀔 수 있다.
- 고정은 안전을 보장하지 않는다. changelog도 잠그기 전에 의존성을 리뷰하라고 따로 적었다.
- 항목이 없거나 어긋났을 때 실행이 어떤 오류로 실패하는지는 확인한 문서에 나오지 않았다.

## 5. 도입한다면 이 순서로

Enterprise Cloud를 쓰는 팀이라면 이렇게 시작하는 게 무난해 보인다.

1. 배포 권한이나 시크릿을 쓰는 워크플로부터 하나씩 온보딩한다.
2. `gh actions-lock` 결과로 생긴 lockfile과 워크플로 변경을 PR로 올려 리뷰한다.
3. 로컬 경로 액션(`./.github/actions/...`)을 쓰는 워크플로가 있는지 먼저 확인한다.
4. 공용 재사용 워크플로 저장소에도 lockfile을 만든다.
5. Dependabot의 actions 업데이트가 켜져 있는지 확인해 lockfile 갱신을 자동화한다.
6. 안정되면 조직 단위로 Require lockfile 정책을 검토한다.

기존에 SHA 핀을 박아 둔 저장소라면 당장 바꿀 이유는 크지 않다. 다만 전이 의존성까지 고정되고 저장소 ID까지 검증한다는 점은 SHA 핀으로는 얻지 못하던 부분이라, 정식 출시되면 옮겨 갈 만하다고 본다.
