Go 1.27부터 `net/http.Transport`가 읽지 않고 닫은 HTTP/1 응답 바디를 백그라운드에서 대신 비워 준다. 최대 50ms 또는 256KB까지다. 그 덕분에 상태 코드만 보고 바디를 버리는 코드도 커넥션을 재사용하게 됐다. Go 1.26까지는 이런 경우 커넥션을 버리고 매번 새로 TCP·TLS 핸드셰이크를 했다. 10월 14일 Go 블로그에 올라온 글에서는 HTTP/1로 100번 호출하는 예제가 약 710ms에서 150ms로, 거의 5배 빨라졌다.

> 왜 바디를 안 읽으면 커넥션이 재사용되지 않았고, 1.27에서는 우리 코드에서 무엇을 정리하면 되나?

> 이 글은 Go 블로그의 "Better HTTP/1 connection reuse"(Nicholas Husin, Damien Neil)를 읽고 정리했다. 글에서도 이 동작은 이후 버전에서 바뀔 수 있다고 적고 있다.

## 1. 왜 커넥션이 버려졌나

HTTP/1 커넥션 하나에서는 응답이 줄지어 온다. 다음 응답이 어디서 시작하는지 알려면 지금 응답의 바디를 끝까지 읽어야 한다. 글의 표현대로 `net/http`는 현재 응답 바디를 끝까지 읽은 뒤에야 다음 응답의 시작을 찾을 수 있다.

그래서 바디를 다 읽지 않고 `Close()`를 부르면 Transport는 그 커넥션을 더 쓸 수 없다고 보고 버렸다. 다음 요청은 새 커넥션을 연다. 비용은 생각보다 크다.

| 단계           | 왕복 시간(RTT)               |
| -------------- | ---------------------------- |
| TCP 핸드셰이크 | 1 RTT                        |
| TLS 핸드셰이크 | TLS 1.2는 2 RTT, 1.3은 1 RTT |

글의 예시처럼 RTT가 100ms인 구간이라면 TLS 1.2 기준으로 연결 설정에만 300ms 정도가 들고, 그다음에야 HTTP 요청이 나간다. 요청 자체보다 준비가 더 오래 걸리는 셈이다.

HTTP/2는 해당이 없다. 스트림이 다중화돼 있어서 한 스트림의 바디를 안 읽어도 다른 요청을 막지 않는다. 내부 서비스끼리 평문 HTTP/1.1로 통신하거나, HTTP/2를 지원하지 않는 외부 API를 부르는 경우가 이 문제에 걸린다.

## 2. 생각보다 흔한 두 가지 경우

글이 든 사례는 둘이다.

### 상태 코드만 확인하는 호출

헬스 체크나 웹훅 전송처럼 상태 코드만 보면 되는 코드가 대표적이다.

```go
func getStatus(url string) (int, error) {
    resp, err := http.Get(url)
    if err != nil {
        return 0, err
    }
    defer resp.Body.Close()
    return resp.StatusCode, nil
}
```

바디를 읽지 않으니 Go 1.26까지는 호출할 때마다 새 커넥션이었다.

### json.Decoder로 읽은 응답

이쪽이 더 눈에 안 띈다. `json.NewDecoder(resp.Body).Decode(&v)`는 닫는 `}`까지만 읽고 멈춘다. 서버가 JSON 뒤에 줄바꿈 하나를 붙여 보내면 그 한 바이트가 남아서 바디를 끝까지 읽은 게 아니게 된다. **바디를 다 읽었다고 생각한 코드도 사실은 커넥션을 버리고 있었을 수 있다.** 개인적으로 이 부분이 가장 놀라웠다. Go 서버만 해도 `json.Encoder`가 값 뒤에 줄바꿈을 붙여 쓴다.

## 3. 그동안 쓰던 우회 코드

이 문제를 아는 팀은 직접 바디를 비우는 헬퍼를 넣어 왔다. 글은 그 헬퍼가 점점 복잡해지는 과정을 보여 준다.

1. `io.Copy(io.Discard, resp.Body)`로 끝까지 읽기. 바디가 크면 새 커넥션을 여는 것보다 비싸다.
2. `io.CopyN(io.Discard, resp.Body, 256<<10)`으로 256KB까지만. 바디가 천천히 흘러오면 여전히 멈춘다.
3. 50ms 타임아웃 추가. 호출한 쪽이 그동안 막힌다.
4. 백그라운드 고루틴에서 비우고, 타임아웃이 지나면 닫기.

흔히 보던 코드는 1번이나 2번 형태다.

```go
defer func() {
    io.CopyN(io.Discard, resp.Body, 256<<10)
    resp.Body.Close()
}()
```

글은 이런 우회 코드가 실수하기 쉬웠고, 필요 없는 HTTP/2 바디까지 비우는 경우도 있었다고 지적한다.

## 4. Go 1.27에서 바뀐 동작

Go 1.27의 Transport는 위 4번을 표준 라이브러리 안에서 대신 한다.

- 읽지 않은 HTTP/1 응답 바디를 비동기로 비운다.
- 상한은 50ms 또는 256KB다. 둘 중 먼저 걸리는 쪽에서 멈춘다.
- 응답에 `Connection: close` 헤더가 있으면 어차피 재사용할 수 없으니 비우지 않는다.

글이 권하는 방식은 단순하다. 다 쓴 바디는 닫기만 하고 나머지는 Go에 맡긴다. 새로 생긴 API나 설정 필드는 없고, 글에는 동작을 끄는 GODEBUG 옵션도 나오지 않는다. 벤치마크는 index.golang.org에 `getStatus`를 100번 호출하는 방식이었고, `GODEBUG=http2client=0`으로 HTTP/1을 강제해서 Go 1.26 약 710ms, Go 1.27 약 150ms가 나왔다.

## 5. 우리 코드에서 볼 것

1.27로 올렸거나 올릴 예정이라면 이 정도를 보면 된다.

- `resp.Body.Close()`가 빠진 곳이 없는지. 자동 비우기는 닫아야 동작한다
- 직접 만든 drain 헬퍼는 HTTP/1 용도라면 이제 없애도 된다. 남겨 둬도 동작은 한다
- 256KB보다 큰 바디를 읽지 않고 버리는 호출은 여전히 커넥션을 버릴 수 있다
- 내부 서비스 간 통신이 HTTP/1.1인지 HTTP/2인지. HTTP/1.1이면 이번 변경의 효과가 크다
- 커넥션 수나 TLS 핸드셰이크 지표를 보고 있다면 1.27 배포 전후로 비교해 볼 만하다

동작이 Transport 안으로 들어갔다는 게 제일 반갑다. 서비스마다 조금씩 다르게 만들어 두던 drain 코드를 표준 라이브러리가 대신하니, 버전만 올려도 HTTP/1 클라이언트가 많은 서비스는 지연이 줄 것 같다.
