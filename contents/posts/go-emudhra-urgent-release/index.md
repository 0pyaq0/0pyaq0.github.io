Go 팀이 10월 26일 eMudhra 중간 CA 키 노출 사건에 어떻게 대응했는지 공개했다. 결론은 단순하다. TLS 연결을 하는 Go 바이너리는 Go 1.27.3 또는 1.26.10으로 **다시 빌드해서 배포해야** 노출된 중간 CA가 발급한 인증서를 거부한다. Python이나 Node.js는 런타임과 CA 번들을 올리면 되지만, Go는 수정이 표준 라이브러리 안에 들어가 바이너리에 같이 묶이기 때문이다. 특히 Linux 서버에서 도는 Go 서비스가 해당된다. Go가 이 건을 처음으로 URGENT 트랙 릴리스로 낸 이유도 거기에 있다.

> Go 서비스는 이 사건에 대해 무엇을 확인하고 무엇을 다시 배포해야 하나?

> 이 글은 Go 블로그의 사건 대응 글을 확인해 정리했다. 사건 자체는 지난번 eMudhra 중간 CA 정리 글에서 다뤘고, 여기서는 Go 쪽 대응만 적는다.

## 1. 사건 요약

10월 17일 Mozilla가 eMudhra 중간 인증서 8개를 OneCRL에 올렸다. 6개는 TLS용, 2개는 코드 서명용이다. 키가 너무 약해서 개인키를 마이크로초 단위로 복원할 수 있었고, eMudhra 루트가 대부분의 루트 프로그램에 들어 있었기 때문에 복원한 키로 아무 도메인의 TLS 인증서나 만들 수 있었다. 중간자 공격이 가능했다는 뜻이다.

## 2. 왜 Go는 서둘러야 했나

Go 블로그는 플랫폼마다 인증서 검증 방식이 다르다는 점을 짚는다.

| 플랫폼         | 인증서 검증 주체  |
| -------------- | ----------------- |
| Windows, macOS | 플랫폼 API에 위임 |
| Linux          | Go 자체 검증기    |

Windows와 macOS는 OS가 폐기 정보를 받아 막아 준다. Linux에는 플랫폼 검증 API가 없어서 Go가 직접 검증하는데, 공통으로 쓸 수 있는 폐기 메커니즘도 없다. 이게 긴급 릴리스를 낸 주된 이유라고 Go는 설명한다. 서버 쪽 Go 서비스는 대부분 Linux 컨테이너에서 돌기 때문에, **실무에서 영향받는 쪽이 정확히 이 경우다.**

개인적으로는 이 대목이 가장 와닿았다. Go 바이너리는 의존성이 적고 정적으로 묶이는 게 장점인데, 이번처럼 신뢰 판단 로직이 바이너리 안에 들어가 있으면 OS를 업데이트해도 바이너리를 다시 빌드하기 전까지는 수정이 반영되지 않는다.

## 3. 대응 과정

Go는 10월 19일 URGENT 트랙으로 Go 1.27.3과 1.26.10을 냈다. 이 트랙을 쓴 건 처음이다. Go 보안 정책 문서를 보니 URGENT 트랙은 생태계 무결성을 위협하거나 실제로 악용돼 큰 피해를 내는 문제에 쓰고, 비공개로 고친 뒤 사전 예고 없이 바로 전용 보안 릴리스를 낸다. 보통의 PRIVATE 트랙이 다음 정기 마이너 릴리스에 수정을 넣고 3~7일 전에 golang-announce로 예고하는 것과 다르다. 시간대별로 보면 이렇다(10월 19일, 미국 태평양 시간).

| 시각  | 일                                                     |
| ----- | ------------------------------------------------------ |
| 11:45 | 외부 연구자가 Go 보안팀에 알림                         |
| 12:30 | Mozilla도 별도로 알리며 즉시 공개는 미뤄 달라고 요청   |
| 14:00 | 복원한 키로 서명한 인증서로 패치 검증 완료             |
| 15:00 | 릴리스 절차 시작                                       |
| 19:13 | 릴리스 공개. 악용을 막으려 패치 설명은 일부러 모호하게 |

연구자들이 약한 키를 공개한 건 다음 날인 10월 20일 아침이다. 알림부터 릴리스까지 7시간 반이 안 걸렸고, 릴리스 절차 자체는 4시간 15분 정도였다고 한다.

Go는 반성할 점도 적었다. 릴리스 절차를 시작할 때 URGENT 릴리스를 미리 예고했다면 사용자가 몇 시간이라도 준비할 수 있었을 것이라는 점이다. 이후 릴리스 절차를 더 빠르게 바꿨고, Windows, macOS와 맞추기 위해 Linux 폐기 지원을 우선순위에 올렸다. 그 후보로 upki 프로젝트를 검토 중이다.

## 4. 확인할 것

Go 블로그가 권하는 순서대로 옮겼다. 먼저 툴체인과 이미 배포된 바이너리가 어떤 버전으로 빌드됐는지 본다.

```bash
go version
go version -m ./my-service
```

govulncheck로 바이너리를 직접 검사할 수도 있다.

```bash
GOTOOLCHAIN=go1.27.3+auto go install golang.org/x/vuln/cmd/govulncheck@latest
govulncheck -mode=binary ./my-service
```

블로그는 TLS 연결을 하는 모든 바이너리를 최신 마이너 릴리스로 올리라고 한다. gRPC처럼 의존성을 통해 TLS를 쓰는 경우도 포함된다. 점검 항목을 추리면 이렇다.

- CI의 Go 툴체인 버전이 1.27.3 또는 1.26.10 이상인지
- 빌드 이미지(`golang:` 베이스 이미지 등)가 고정된 옛 태그를 가리키고 있지 않은지
- 이미 배포된 바이너리를 `go version -m`으로 확인했는지
- 오래 재배포하지 않은 내부 도구, 사이드카, CLI도 대상에 넣었는지
- Linux에서 도는 바이너리를 우선 재빌드했는지
